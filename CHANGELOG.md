### Added
- **Bulk photo uploads no longer freeze the UI — downscale/encode now runs in a Web Worker pool** — image decode, downscale (to ~2048 px), and JPEG encode now happen off the main thread in `photo-worker.js`, a new same-origin ES-module worker. `createWorkerDownscaler({ spawn, poolSize=2, timeoutMs=8000 })` spawns a pool of workers and is exported for testing; `getWorkerDownscaler()` is the lazy module-level singleton wired into `buildOnAddPhotos`. A **per-call `downscaleRouted` wrapper** probes the pool's readiness on every file and falls back to main-thread `downscaleImageThrottled` (which yields a macrotask between files) on iOS ≤16 / any environment without OffscreenCanvas-in-worker — so the upload flow remains correct on older devices. An **EXIF-read yield** (`setTimeout(0)` between per-file capture-date reads) was also added to keep the UI responsive during the bucket phase. `photo-worker.js` is added to `PRECACHE_URLS` in `sw.js` so it's available offline after the first load. The worker is **never imported in Node** (browser-only dynamic import path), so `node --test` stays **network-free**. `CACHE_VERSION` bumped **v30 → v31** (`app.js` + `photo-worker.js` added; `sw.test.js` pinned assertion updated in lockstep). Suite is now **451 total** (was 437), all passing.

- **Live shared reminisce gallery — past days now show everyone's uploaded photos** — the reminisce-framing photo gallery (the "Engawa Scroll" view of a past day) is now **live and shared**. It merges the hand-authored `day.photos` with travelers' **uploaded** photos for that date — read from Firestore via a real-time `onSnapshot` listener — so a photo someone adds shows up in the day's gallery without a reload, and the gallery is **offline-readable** from the local cache after the first load. Authored photos render first; uploaded photos follow, sorted by capture time. This depends on `photo-upload-flow` (it reads the `photos` docs that flow writes) and **requires the `firebase-photo-rules` deployment** — the Firestore listener reads the documents those rules govern.
  - The reminisce branch now has a real `start()`/`stop()` lifecycle: it subscribes on `start()`, re-renders the grid + the "N photos" seam count + rebuilds the lightbox on each snapshot, and unsubscribes on `stop()`. A snapshot that arrives **while the lightbox is open** is deferred and applied on close (a new optional `opts.onClose` on `buildLightbox`), so an open viewer is never yanked out from under you. A quiet pulsing **loading affordance** (`.reminisce-loading-note`) shows only while the first snapshot is pending on a day with no authored photos.
  - New public exports: `mergeGalleryPhotos(authored, uploaded)` — a pure merge (authored-first, uploads sorted by `takenAt` ascending, deduped by URL, capped at `REMINISCE_GALLERY_MAX = 12`, each normalized to `{ url, alt }` with uploaded photos credited `"Photo by <uploader>"` and every URL validated through `safeUrl`); and `setSubscribePhotos(fn)` — a module-level injection seam for the live listener. **When the seam is absent** (every existing test, and any non-Firebase host) the reminisce view renders the authored photos **synchronously, byte-identical to before** — the live layer is purely additive.
  - The `boot()` `photoService` gained `subscribePhotos(iso, cb)` (an `onSnapshot` of `photos` docs where `date == iso`, returning the unsubscribe function) and added `onSnapshot` to the lazy Firestore imports. **No Firestore re-init** — it reuses the `persistentLocalCache` Firestore instance `photo-upload-flow` established at first init, so offline reads come straight from the cache.
  - `RUNTIME_MAX_ENTRIES` in `sw.js` raised **60 → 140** to keep several days of merged galleries warm offline (4 travelers × up to 12 photos/day, plus fonts/Firebase-SDK), FIFO-evicting the oldest. `CACHE_VERSION` bumped **v27 → v28** (`app.js` + `index.html` changed; the pinned `sw.test.js` assertion updated in lockstep). All Firebase SDK loads stay **lazy / browser-only**, so `node --test` remains **network-free**. Suite is now **437 total** (was 419), all passing.

- **One-tap photo upload — the ☰ "Add photos" row now does something** — the day-nav hamburger's **Add photos** seam (previously a disabled placeholder) is now wired to a real handler injected through `mountApp(root, { onAddPhotos })`. The flow: a multi-select native picker → read each photo's EXIF `DateTimeOriginal` → bucket by trip day → downscale (orientation-corrected, ~2048 px max, JPEG ~0.85) → upload to Firebase Storage at a **unique** path `trip-photos/<date>/<uploader>/<uuid>.jpg` (a photo can never overwrite another) → write a Firestore `photos` doc `{ date, uploader, storagePath, url, takenAt, size, createdAt }`. Photos outside the trip window are skipped; re-selecting an already-uploaded photo is best-effort **deduped** (composite key `uploader + EXIF datetime + original file size`, checked **before** any decode/upload, so a re-add is a fast no-op). A once-per-device **"Who's uploading?"** prompt (from `TRIP.travelers`, persisted to `localStorage['jt:uploader']`) attributes uploads; a **progress sheet** ("Adding N of M…") + an **end summary** report the run; photos with no readable EXIF route to a single **batch date-correction** (default = the viewed day) so nothing is silently filed on the wrong day. Per-file errors are non-fatal; double-taps are guarded.
  - **Firebase Storage + Firestore are now initialized** (reusing the existing `boot()` Firebase `app`; never a second `initializeApp`). This task owns the **first Firestore init**, so it uses `initializeFirestore(app, { localCache: persistentLocalCache(...) })` — enabling the offline cache the later gallery task needs (a plain `getFirestore` first would make that un-retrofittable).
  - New public exports (for tests + the downstream gallery task): `readCaptureDate`, `readExifDateTimeOriginal`, `exifDateTimeString`, `bucketDateFromExif`, `compositeKey`, `decideFile`, `summarizeRun`, `sanitizePathSegment`, `getUploader`, `setUploader`, and the injected-seam orchestrator `wirePhotoSync(deps)` → `{ run(currentIso) }`.
  - All Firebase SDK loads stay **lazy / browser-only** (Firestore + Storage modules join the existing dynamic `import()` inside the `typeof document !== 'undefined'` boot block), so `node --test` remains **network-free**. Suite is now **419 total** (with `sw.test.js`). `CACHE_VERSION` bumped **v26 → v27** (`index.html` + `app.js` changed). *Note: live uploads require the `firebase-photo-rules` (Storage/Firestore rules) to be deployed, and displaying uploaded photos is a later task (`reminisce-gallery-live`).*

### Added
- **Password-only auth gate** — the app is now behind a single shared Firebase password. A full-page login overlay (`#login-overlay`, wrapping `#login-form`, in `index.html`) sits in front of `<main id="app-root">`; the app is invisible until Firebase confirms the user is signed in. On submit, `signInWithEmailAndPassword(SHARED_EMAIL, typed)` authenticates against the shared Firebase account. `onAuthStateChanged` drives the reveal: authenticated → hide the gate + boot `mountApp`; signed out → show the gate + tear down the app. Firebase's default `browserLocalPersistence` keeps each device signed in across page reloads without any additional code. Security is enforced server-side by Firebase Auth and the already-deployed Storage/Firestore rules (`request.auth != null`); the password gate is the user-facing expression of those rules. Native form submit is blocked (`onsubmit="return false"` in HTML + a JS guard) so the password can never leak into the URL. A "Wrong password" inline error message renders on bad credentials; the submit button shows a "Signing in…" label during the request.
- **`firebase-config.js`** — new tracked file containing the non-secret Firebase web SDK configuration (API key, project ID, app ID, etc.). These values identify the Firebase project and are safe to commit; they carry no privileges on their own. The real access control is the auth password and server-side security rules. `firebase-config.js` is now precached by the service worker so the gate works offline after the first visit.
- **Firebase Modular SDK (10.12.5) via gstatic CDN** — loaded via a dynamic `import()` from the pinned `https://www.gstatic.com/firebasejs/10.12.5/` URLs (Auth module only). No npm, no build step — consistent with the project's no-dependency constraint. The SDK is runtime-cached by `sw.js` (stale-while-revalidate, same `runtime-v<CACHE_VERSION>` bucket as photos/fonts) so subsequent visits and offline use load the SDK from cache.
- **`CACHE_VERSION` bumped v23 → v24** — `firebase-config.js` is a new precached shell file; bumping invalidates installed caches so users pick up the gate on their next visit.
