# Japan Trip Companion

Data-driven static site for an 18-day Japan trip — a daily companion for 4 travelers (2 couples). Deployed via GitHub Pages. No build step.

## Trip Status

**Flights booked: June 16 - July 3, 2026 (in/out of Tokyo).**

The site renders from `data/days.js`. **All 18 days are authored (Jun 16 – Jul 3), contiguous, no gap.** The trip content is complete end-to-end: Tokyo (Jun 16–21), Hakone (Jun 22–23), Kyoto and the return leg (Jun 24 – Jul 3). `dayNumber` is derived from `TRIP.start` (Jun 16 = Day 1), so the days run Day 1 (Jun 16) → Day 18 (Jul 3). The scaffold still degrades gracefully if a day is ever removed (absent days return `null`, no crash).

## Tech Stack

- Static site, **no build step**: plain HTML/CSS + ES modules served as files.
- Content lives in a single data module (`data/days.js`); `app.js` validates and renders it.
- Tests via Node's built-in runner (`node:test`) — **no npm, no dependencies**.
- Fonts: Manrope + Playfair Display (Google Fonts). Theme: ukiyo-e / washi / Great Wave.
- **PWA**: installable + works offline via a hand-written service worker (`sw.js`) + `manifest.json` — no PWA tooling/build.
- GitHub Pages deployment.

## Architecture

Data-driven, single render pipeline:

```
data/days.js   ← TRIP + DAYS (content; the only file you edit to change the trip)
     │ import
     ▼
app.js         ← validate → deep-freeze → derive dayNumber → public API + mountApp() (clock-driven landing + nav)
     │ <script type="module">
     ▼
index.html     ← slim shell: theme CSS + <main id="app-root"> (render target)
```

### Data schema (`data/days.js`)

```js
export const TRIP = { title, start, end, travelers: [..], eveningWindow: { startHour, endHour } };
export const DAYS = [{
  date,                       // ISO "YYYY-MM-DD"; dayNumber is DERIVED (do NOT author it)
  base, title, intro,
  spend,                      // optional
  photos: [{ url, alt, credit }],          // [] = none
  lodging: { name, address, mapUrl, coords?, breakfast? } | null,
  prep: [".."],               // free-text; powers the evening "Prep for tomorrow"
  dayParts: { morning?, afternoon?, evening? },  // optional; one-line summaries for collapsible section headers (only non-empty buckets)
  plan: [{
    time?, tag, title, note?, mapUrl?, coords?, reserved?,   // reservations = reserved:true
    transit?: TransitLeg & { minutes?, transfer?: TransitLeg },  // optional; only for tag:'transit' items — renders a structured line / stops / minutes block
    recommendations: [{ name, pros: [".."], con, mapUrl?, coords?, address?,
                        transit?: TransitLeg & { minutes, transfer?: TransitLeg } }], // MAX 4; transit? for recs whose walk from anchor exceeds 1.5km
                        // GOTCHA: for a NON-walkable transfer rec (airport→city, long-haul), OMIT `coords`.
                        // With coords, the walk-distance origin falls back to lodging and prints a misleading
                        // "N min from <hotel>" line on a leg that travels TO the hotel. Without coords the
                        // transit pill renders standalone (the correct display for transfers).
                        // SAME GOTCHA on a TRANSITION/CHECKOUT DAY: `day.lodging` is the NIGHT's lodging, so a
                        // first-of-day meal/coffee rec (no preceding plan item with coords → falls back to lodging)
                        // anchors to a lodging that may be far away (e.g. Jun 22 breakfast in Akasaka but that
                        // night's lodging is Senkyoro in Hakone → "999 min from Senkyoro"). OMIT `coords` on those
                        // recs so the card renders standalone; keep `mapUrl`. Recs with a real preceding anchor
                        // (e.g. Jun 23 lunch after the Open-Air Museum) keep coords and show a correct distance.
  }],
}];
// TransitLeg = { mode: 'bus'|'train'|'subway', line?, from, to }
// Tags: meal | transit | sight | checkin | reservation | rest | bar | spa | checkout
// MULTI-LEG GOTCHA: for a `transfer`, the PRIMARY leg's `to` must be the
// INTERCHANGE station (= transfer.from), NOT the final destination — the renderer
// draws stops as `from → to → transfer.to`, so authoring the destination on the
// primary `to` prints a duplicated terminal stop (e.g. "Akasaka → Tsukiji → Tsukiji").
// Author per-leg `minutes` on BOTH legs (they sum). See the Universal→Nishikujo→Osaka-Namba
// leg for the canonical shape; an invariant test in app.test.js guards every multi-leg item.
```

Conventions baked into the data: reservations are plan items with `reserved:true` (no separate field); there is **no `status` field** — a sparse day = empty `plan`/`photos`. See `README.md` for an annotated example and field-by-field docs.

### `app.js` public API (downstream screen tasks build on this)

- `getTrip()` → frozen `TRIP`.
- `getDays()` → fresh array of validated, date-sorted, deeply-frozen days (each with derived `dayNumber`).
- `getDay(iso)` → the day for an ISO date, or `null` if absent (e.g. a date outside the trip window). The trip is now fully authored, so every in-window date resolves to a day.
- `getDayByNumber(n)` → day by derived `dayNumber`, or `null` (non-finite input → `null`).
- `renderDay(day, framingName = 'plan')` → returns `{ node, start, stop }`. Mount `node`, call `start()` to begin the hero slideshow, call `stop()` before discarding. Framings: `'anticipation'`, `'plan'`, `'reminisce'`. Null/absent day renders a placeholder. The plan list is split into three collapsible `<section class="day-part">` blocks (Morning / Afternoon / Evening) — all collapsed by default; click a header to expand. Non-empty buckets only; `day.dayParts` summaries appear in the collapsed header.
  - **Reminisce framing ("Engawa Scroll" → "Seigaiha mosaic")** is distinct: it **drops the hero slideshow**, wraps the header in a blue "memory frame" (`.reminisce-frame`, no sepia/amber tint), and flows into a **75vh internally-scrollable 3-column square mosaic gallery** (`buildReminisceGallery`, `REMINISCE_GALLERY_MAX = 1000` sanity ceiling — in practice shows every uploaded photo) inside a stable `.reminisce-gallery-host` div (`max-height:75vh; overflow-y:auto; overscroll-behavior:contain`; top/bottom mask-image edge fade, host border removed). The grid (`.reminisce-gallery`) is `repeat(3, 1fr)` / `grid-auto-rows: 31vw` / 6px gap / `grid-auto-flow: row dense`, card-bleeding to the full day-view card (~372px of a 390px screen). Tiles are `<button>`s; the **square (`object-fit: cover`) is the default**, with two punctuating shapes: a **2×2 crest** (`.gallery-tile-feature`, ~1-in-7 photos chosen by `fnv1a(url) % 7 === 3` — hash-stable across re-sorts, indigo `outline` hairline) and a full-row **3×1 panorama** (`.gallery-tile-pano`, only for photos with stored dims and w/h ≥ 1.7 — **panorama outranks crest**; dim-less photos → plain square). Span classes come from a single `assignTileSpans(photos)` pass whose backward credit-demotion algorithm guarantees the `row dense` layout is **provably hole-free** (proven by an exact dense-placement simulator property test). Tile radius 6px; an iOS-26-only scroll-driven tide-line sits behind `@supports (animation-timeline: scroll())` + `prefers-reduced-motion: no-preference`. Tapping a thumbnail opens a swipeable full-screen **lightbox** (`buildLightbox`: CSS scroll-snap track + live counter + Esc/arrow keys + focus trap; optional `opts.onClose` fires on **user-driven** close only, not on `destroy()`; slides are `loading="lazy"` + `preloadNeighbors` for i±1) that **mounts on `document.body`** when opened — NOT inside the day view — to escape `.day-view`'s `backdrop-filter`/`overflow:hidden` containing block; `stop()` tears it down.
    - **Gallery is uploads-only (exclude-authored-from-reminisce task):** the reminisce gallery shows **only travelers' uploaded photos** — authored/stock `day.photos` are excluded (they still drive the anticipation/plan hero slideshow). A past day with no uploads shows the empty-state note. The render path calls `mergeGalleryPhotos([], docs)` — passing an empty authored array — so `mergeGalleryPhotos` itself is unchanged. **When `setSubscribePhotos` is absent** (every unit test, any non-Firebase host) the gallery renders the **empty-state immediately** — not authored photos. **When live**, the seam reads `"Loading…"` while the first snapshot is pending (not "No photos yet"), then updates to the real count on snapshot arrival.
    - **Live lifecycle (reminisce-gallery-live task):** the reminisce branch has a **real `start()`/`stop()` lifecycle** that subscribes via the injected `setSubscribePhotos(fn)` seam on `start()`; on each Firestore `onSnapshot` it re-renders the grid + the "N photos" seam count + **rebuilds the lightbox** (the lightbox captures its array at build time, so a stale one is a bug), and unsubscribes on `stop()` (folded beside the lightbox teardown; `stopActiveDayView()` calls `stop()` on every nav → no leak). A snapshot that arrives **while the lightbox is open** is deferred (`pending`) and applied on close via `onClose` — never yanking an open viewer. Live display still needs `firebase-photo-rules` deployed (the listener reads the `photos` docs those rules govern).
- `mountApp(rootEl, opts = {})` → **the bootstrap mount entry point.** Picks the landing view from the clock (`pickLandingView`), mounts it, and wires the day-nav bar + evening "Prep for tomorrow" button. The day-nav (`buildNavBar` → `buildNavMenu`) is: a **☰ hamburger menu** (left, grid col 1) carrying **Home** (→ `toOverview()`) + **Add photos** rows, a centered `day-nav-pos` label, and **prev/next circular chevrons** (`day-nav-prev`/`day-nav-next`, right) — grid stays `1fr auto 1fr`. The ☰ popover is **body-mounted** (escapes `.day-nav`'s `backdrop-filter` containing block, same trick as `buildLightbox`), with a focus trap and close-on outside-click/Esc/scroll/resize/activation; `stopActiveDayView` tears it down (via `activeNavMenuDestroy`) on navigation. `opts.onAddPhotos(iso)` is the **injected seam** for the Add-photos row — it receives the currently-viewed day's ISO, and the row is **disabled when the handler is absent OR before the trip starts** (`tripHasStarted()`, clock-seam-gated). The bootstrap now wires a **real handler** here (`boot()` → `buildOnAddPhotos(photoService)` → the photo-upload flow below); single-arg `mountApp(rootEl)` is fully backward-compatible. Returns a controller `{ go(index), toIso(iso), toOverview(), destroy() }`. `go`/`toIso` are clamped to the trip window; `toOverview()` re-mounts the 18-day overview from any day view (same code path as the initial pre-trip overview, fresh `daysUntil` per call); `destroy()` stops the active slideshow and clears the root. This is what `index.html` boots — `renderInto` is no longer the bootstrap path.
- `renderInto(rootEl, day?, framing?)` → mounts a *single* day view (defaults to Jun 24, `'plan'`). Stops any prior view's slideshow before mounting. **Retained for backward compatibility / standalone use**, but `mountApp` is the live entry point.
- Date/time-aware navigation (date-time-aware-navigation task):
  - `frameForDay(day, now = getNow())` → `'anticipation'` (future) / `'plan'` (today) / `'reminisce'` (past), by **local calendar day** (accepts a day object or ISO string; bad input → `'plan'`).
  - `pickLandingView(now = getNow())` → `{ view:'overview', day:null, daysUntil }` before the trip, `{ view:'day', day, framing }` during/after.
  - `isEveningWindow(now, window = getTrip().eveningWindow)` → boolean; the window **wraps midnight** (`hour >= startHour || hour < endHour`; default 21→4).
  - `tripWindowDates(trip = getTrip())` → ordered ISO array of every trip day (18 days Jun 16–Jul 3); `[]` on an inverted/unparseable window.
  - `getNow()` / `setNow(fn|null)` → the clock seam. **All "now" reads go through `getNow()`** so the clock is overridable (the time-travel test mode and tests pin it). `getNow()` degrades to the wall clock if the provider throws or returns a non-Date. `setNow(null)` restores.
- Time-travel test mode (time-travel-test-mode task):
  - `parseNowOverride(value)` → parses a datetime-local string (or any `new Date()`-parseable string) into a valid `Date`, or `null` if unparseable. Local-time parse is intentional.
  - `resolveNowOverride()` → reads the override from URL param `?now` (wins) then `localStorage` key `jt:now`, pins the clock via `setNow()` when one is valid, and returns the active override `Date` or `null`. **Inert by default** — no override means the real device clock is used. Clear tokens (`?now=clear`, `off`, `real`, `reset`, empty) wipe the stored override and restore the real clock. Node-safe (guarded on `typeof window`). Called once at module load; `buildTimeTravelBanner()` (internal) renders the active-override indicator in `index.html`.
- Pre-trip home (trip-overview-home task):
  - `renderOverview(daysUntil, onEnter)` → builds the pre-trip **home screen** and returns `{ node, start, stop }` (start/stop are no-ops — no slideshow). The `{view:'overview'}` landing descriptor maps here. It renders a **live countdown** with three states off `getNow()` (before: "N days until the trip"; during: "The adventure is underway."; after: "The adventure is complete.") plus a **tappable index of all 18 trip days** — each row shows Day#, date, city/region, and a "Planned"/"TBD" status pill; tapping a row calls `onEnter(iso)` (wired to `mountApp`'s `toIso`) to navigate into that day. With the trip now fully authored, every row resolves from `day.base` and shows "Planned". Exported for tests.
- Photo upload (photo-upload-flow task): the ☰ "Add photos" seam now does real work. `boot()` lazily builds a module-level `photoService` (reusing the existing Firebase `app`; **first Firestore init** uses `initializeFirestore(app, { localCache: persistentLocalCache(...) })` to own offline persistence for the later gallery — never `getFirestore` first, which would make it un-retrofittable) and `getStorage(app)`; `mountTheApp` reads it via `buildOnAddPhotos(photoService)` and passes `mountApp(root, { onAddPhotos })`. Flow: multi-select picker → **`wirePhotoSync.run()` mounts the progress sheet immediately on entry** (indeterminate "Preparing photos…" state, bar hidden — kills the dead-air gap between picker-close and feedback; picker-cancel/offline mount nothing, every post-mount exit settles the sheet) → EXIF `DateTimeOriginal` per file, read from a **128 KB header slice** (`EXIF_SCAN_BYTES = 131072`, `file.slice` at the call site — JPEG APP1 caps at 65,533 bytes; Apple worst-case header ≈68 KB) with a `setTimeout(0)` yield between reads to keep the UI responsive → bucket by trip day (**no EXIF in the slice → null → silently bucket by the file's `lastModified` day; the batch date-correction prompt fires only when even that hint is unavailable, never as the default for a missing slice**) → window-filter + pre-decode dedup → flip the sheet to the counting "Adding N of M…" bar at upload start → downscale (~2048px, JPEG ~0.85, orientation-corrected; **worker-backed by default** — `buildOnAddPhotos` uses a per-call `downscaleRouted` wrapper that probes the worker pool's readiness and falls back to main-thread `downscaleImageThrottled` on iOS ≤16 / environments without OffscreenCanvas-in-worker; a worker downscale **FAILURE** (`{downscaled:false}`) gets exactly ONE retry on the genuinely different main-thread decoder before bailing — the not-ready route is unchanged, no same-decoder retry) → upload to a unique `trip-photos/<date>/<uploader>/<uuid>.jpg` (on the **bail path** where both decoders failed, the loop uploads the ORIGINAL bytes labeled honestly by `sniffImageType`: true extension on the path — `.heic`/`.png`/…, unknown → `.bin` + `application/octet-stream`, NEVER a false `.jpg` — and the matching contentType on the upload metadata; silent by design, one `console.warn`) → `getDownloadURL` → `setDoc` a `photos` doc `{date, uploader, storagePath, url, takenAt(sortable string), size, createdAt: serverTimestamp()}` (Storage **before** Firestore). Identity is a once-per-device "Who's uploading?" prompt (`getUploader`/`setUploader`, `localStorage['jt:uploader']`, throw-safe). Firebase Storage/Firestore SDKs join the **lazy, browser-only** dynamic `import()` block (`node --test` stays network-free). **Live uploads (and the now-shipped reminisce display, see the live reminisce gallery above) still need `firebase-photo-rules` deployed.**
  - Worker pool: `createWorkerDownscaler({ spawn, poolSize=2, timeoutMs=8000 })` spawns `photo-worker.js` instances (same-origin ES-module workers; OffscreenCanvas-based decode → JPEG encode). `getWorkerDownscaler()` is the lazy module-level singleton, wired into `buildOnAddPhotos`. The worker is **never imported in Node** (browser-only dynamic import path), so `node --test` stays network-free.
  - **Bail-path label gotcha:** the deployed Storage rules require `contentType.matches('image/.*')`, so the `.bin`/`application/octet-stream` fallback (unknown/unreadable header) is **REJECTED by the live rules and tallies as an upload error** — intentional ("never a false label" outranks "upload at any cost") and practically unreachable since `sniffImageType` covers every real camera/picker family (JPEG/PNG/GIF/WebP/HEIC-family/TIFF/BMP; SVG deliberately excluded as script-capable). Do NOT relabel unknown bytes as `image/jpeg` to sneak past the rules.
  - **Multi-container EXIF (speed-up-photo-picker-handoff task):** `readExifDateTimeOriginal` / `readCaptureDate` now read `DateTimeOriginal` from **JPEG + HEIC (ISO-BMFF) + PNG (`eXIf` chunk — covers iOS screenshots)** headers, dispatched by a magic-byte check to per-container locators (`locateTiffInJpeg` / `locateTiffInPng` / `locateTiffInIsoBmff`, with `isHeicFamilyBrand` / `isTiffMagic`) that all feed one shared `readTiffDateTime` TIFF walker. The JPEG path is **byte-for-byte unchanged**. The PNG `eXIf` payload is a **raw TIFF block** (no `"Exif\0\0"` prefix, unlike JPEG APP1). Every locator + the walker are **pure, bounds-checked, NEVER-throw** — any anomaly (bad magic, offset past the 128 KB header slice, truncation, malformed box) → `-1` → `null` → the **unchanged** silent `lastModified` fallback (so dedup/`takenAt`/bucketing/prompts are untouched, they just succeed on more files). HEIC `iloc` parsing **arithmetic-skips** non-target items' extents (DoS hardening against a crafted huge-extent-count file). The picker declares HEIC via the exported `PICKER_ACCEPT = 'image/*,image/heic,image/heif'` const (set on `input.accept` in `pickFilesBrowser`) so iOS hands over original HEIC bytes instead of a 30–60s in-picker transcode; the transcode moves into the existing worker downscale step.

## Conventions

- **No build step, no dependencies.** Keep it plain HTML/CSS/ES modules.
- **Bump `CACHE_VERSION` in `sw.js` whenever you change a precached shell file** (index.html, app.js, data/days.js, manifest, icons). With no build step this is the only cache-busting mechanism — skip it and installed users get stale files until the old cache happens to evict. **LOCKSTEP EDIT REQUIRED:** `sw.test.js` carries a *pinned* assertion (`test('CACHE_VERSION is v<N> …')` + `assert.equal(CACHE_VERSION, 'v<N>')`) that hard-codes the expected version — bumping `sw.js` alone makes that test FAIL, so you must update the pinned title + assertion in `sw.test.js` in the same change. (Most other `sw.test.js` checks derive the version dynamically, but this one is pinned on purpose; confirmed by the v24→v25, v25→v26, and v26→v27 bumps.)
  - **Parallel-branch collision:** `CACHE_VERSION` is a single global, so two tasks that branch from the same `main` will both bump it to the *same* next value (e.g. both v18→v19). The second one merged must re-reconcile to the *next free* version (v19→v20) — otherwise its shell change deploys under a `CACHE_VERSION` that already shipped, and users who cached the first deploy never re-precache it (stale assets). When running tasks in parallel, check `main`'s current `CACHE_VERSION` at merge time, not at branch time. (Lived example: `make-gallery-scrollable` branched at v35 and chose v36, but `minimize-upload-modal` (v36) **then** `harden-uploaded-url-origin` (v37) both merged first — so it reconciled to **v38** at merge, not v36.)
  - **A parallel task can add a *gate inside a shared function* — update your fixtures, not just the version.** When two serial-chain tasks both touch the same hot function, the version bump is the *easy* conflict. The subtle one: `harden-uploaded-url-origin` added a Storage-origin allowlist to `mergeGalleryPhotos`'s `pushSafe` (uploaded URLs whose origin ≠ `https://firebasestorage.googleapis.com` are now **dropped**). After merging it in, `make-gallery-scrollable`'s own new tests — which fed `example.com` *uploaded* docs — silently rendered 0 tiles until every uploaded fixture (incl. the `uploadedDocWithDims` helper) was switched to the Storage origin. **Authored** fixtures stay any origin (the allowlist only gates the uploaded branch). Rule: after a merge that adds validation to a function your tests exercise, re-run the suite and assume any fixture feeding that function may need to satisfy the new gate. `pushSafe`'s signature now carries BOTH features — `(rawUrl, alt, width, height, requireStorageOrigin=false)` — preserve all five params on any future edit.
- **Any file imported at module top level must be precached.** `app.js` does `import { firebaseConfig } from './firebase-config.js'` — a new top-level dependency 404s the whole app offline unless it's added to `PRECACHE_URLS` in `sw.js` (and is git-tracked, since Pages serves only committed files). The auth gate's `firebase-config.js` is tracked + precached for exactly this reason.
- **The Firebase SDK loads from the pinned gstatic CDN** (`https://www.gstatic.com/firebasejs/10.12.5/...`) via a dynamic `import()` inside the browser-only `typeof document !== 'undefined'` boot block — never at module top level (keeps `node --test` network-free). `sw.js` runtime-caches that host so the gate boots offline after the first online load; bump the pinned version in `app.js` AND the `sw.test.js` URL literal together.
- **Firestore persistence must be enabled at the FIRST init — it cannot be retrofitted.** `photo-upload-flow` owns the first `getFirestore`/`initializeFirestore` call, so it uses `initializeFirestore(app, { localCache: persistentLocalCache(...) })` (NOT plain `getFirestore(app)`). Calling `initializeFirestore` AFTER a plain `getFirestore` throws "already initialized" — so a later task (e.g. `reminisce-gallery-live`) cannot add offline cache if an earlier call used the bare getter. The `photoService` handle is built ONCE at module level in `boot()` (because `mountTheApp` lives outside `boot()`, and `onAuthStateChanged` can fire again on sign-out/in — guard against rebuilding). Reuse the existing boot `app` instance; a second `initializeApp(firebaseConfig)` throws.
- **The worker-vs-main-thread downscale decision must be made PER CALL, never baked at mount.** `buildOnAddPhotos` runs ONCE at mount (from `onAuthed`), *before* the worker pool's async readiness probe resolves — so capturing `worker-ready?` there would freeze the slow path on `false` forever. The fix: `buildOnAddPhotos` injects a stable `downscaleRouted(file)` wrapper that, **per call**, races the pool's `ready` promise against a timeout and picks the worker or the main-thread `downscaleImageThrottled` path. Same shape of trap as the `photoService`/`getWorkerDownscaler` singletons being built outside `boot()` because `onAuthStateChanged` re-fires.
- **The worker pool must ALWAYS settle — a hang is worse than the freeze it fixes.** `createWorkerDownscaler`'s `ready` promise and every `downscale(file)` promise resolve on *every* path: worker `{ok:true/false}`, `onerror` (fail-all-pending → original file), per-request timeout (8s → original; a late reply for a timed-out id is a no-op via the `!entry` guard), and a `postMessage` throw. The real `new Worker(new URL('./photo-worker.js', import.meta.url), {type:'module'})` spawn lives ONLY inside the lazy `getWorkerDownscaler()` singleton (browser-only) — never at module top level, so `node --test` never spawns a worker. `photo-worker.js` is precached with the **bare filename** (no `?v=`) so the `new Worker` GET hits the exact-match shell key.
- **An `action`-less login form still submits natively.** Pressing Enter on a focused field before JS wires its handler does a GET `index.html?password=…`, leaking the secret into the URL/history/SW-fetch. Guard it BOTH statically (`onsubmit="return false"` on the `<form>`) and synchronously in JS (`installSubmitGuard`, before any `await`) — a handler installed after `await import(SDK)` is too late.
- All trip data lives in `data/days.js`; editing a day should stay a localized data edit.
- Render is **XSS-safe by construction**: data reaches the DOM via `textContent` / `createElement` only — never `innerHTML` with interpolated data. Preserve this in downstream screens.
- When wiring data URLs (`photos[].url`, `mapUrl`) into `href`/`src` in screen tasks (and especially once v2 adds user-uploaded photos), validate the scheme through `safeUrl()` (rejects `javascript:`/`data:`/etc., allows http(s) + relative) and add `rel="noopener noreferrer"` on external links. **Gotcha:** `safeUrl` strips ASCII tab/LF/CR *before* the scheme check — the WHATWG URL parser strips those characters, so `java\tscript:` would otherwise re-form into a live `javascript:` href. Keep that stripping if you touch `safeUrl`.
- Validation is non-fatal: malformed/absent days warn-and-skip; the site must always render whatever is valid (partial-trip safe).
- **The EXIF capture-date reader parses untrusted image headers — keep it never-throw and bounds-checked.** `readExifDateTimeOriginal`'s per-container locators (`locateTiffInJpeg`/`locateTiffInPng`/`locateTiffInIsoBmff`) and the shared `readTiffDateTime` walker run over arbitrary user-picked bytes (incl. crafted HEIC/PNG). Every read is bounds-checked against the 128 KB header slice and any anomaly collapses to `-1`/`null` (→ silent `lastModified` fallback) — never a throw that would abort the upload run. Preserve this if a future task extends the TIFF tail/IFD walk (HEIC `iloc` already arithmetic-skips non-target extents to avoid a DoS).
  - **Truncation evidence → null; genuine absence → IFD0 fallback. Do not conflate.** When the sub-IFD pointer targets past the slice end, the IFD entry table is cut mid-scan, or a tag's value bytes lie beyond the slice, `readTiffDateTime` returns `null` — NOT `DateTime` (IFD0 tag `0x0132`). `DateTime` is the file's last-edit timestamp; trusting it when the sub-IFD was merely cut off would silently misfill `takenAt`, the gallery sort, and the composite dedup key. The IFD0 `DateTime` fallback is reserved for genuine absence: the sub-IFD is fully readable but does not contain `DateTimeOriginal` (tag `0x9003`), or the `0x9003` entry is malformed (type ≠ 2 / count 0). The invariant: **degraded, never wrong**.
  - **Two sentinels, asymmetric by design — do not unify them.** `readPointer` returns `-1` (number domain) when the IFD0 entry table is cut mid-scan; `readAscii` returns the module-local `EXIF_TRUNCATED` Symbol (string domain) when the IFD start, entry table, or value bytes lie past the slice end. Each sentinel is chosen so it cannot collide with that helper's own legitimate returns — `readAscii` returns strings, so a Symbol can never be mistaken for one; `readPointer` returns unsigned offsets, so `-1` can never be a valid result. Both collapse to the same `null` at the walker's tail; nothing downstream needs to distinguish the two truncation kinds. The Symbol must never escape the walker — the public return type of `readExifDateTimeOriginal` / `readCaptureDate` is `string | null`.
- **Read "now" only through `getNow()`** — never call `new Date()` directly in navigation/landing/time-of-day logic. The clock seam (`getNow`/`setNow`) is the single override point time-travel-test-mode and unit tests depend on; a stray `new Date()` silently bypasses pinned/overridden time. Compare days by **local calendar day** (via `localISODate`/`dayDelta`), not raw timestamps.
- CSS classes use kebab-case; the ukiyo-e theme tokens live in `:root` in `index.html`.
- **Reminisce-mosaic hole-freeness is structural, not incidental — two invariants are load-bearing if you ever touch the gallery span logic.** (1) **Squares must stay the default and big-tile assignment must be LIST-BASED** (`assignTileSpans(photos)` backward credit-demotion pass, `CREST_COST=3`/`PANO_COST=2`), NOT a per-tile `f(width,height)` classifier. `grid-auto-flow: row dense` can only backfill a gap a 2×2/3×1 opens if enough plain squares follow it — a per-tile function structurally cannot see "what follows," so it cannot guarantee no holes (a naive tail-guard was DISPROVEN by simulation at counts 5 and 10). The costs are validated by the exact-`row dense`-placement **property test** in `app.test.js` (exhaustive n≤16 incl. pano flags + 20k seeded-random n≤80 + a mutation check that deletes the demotion pass and asserts a hole appears) — if you change the vocabulary or costs, that test is the authority; never ship it red. (2) **`grid-auto-rows` must be a `vw` unit (`31vw`), never a `%`/`calc(%)`** — percentages resolve against the grid's indefinite block height → `auto` → rows size to lazy-image content → reintroduces the layout-shift the fixed-row grid exists to prevent. Crest selection is `fnv1a(url) % 7 === 3` (hash of the immutable Storage URL, so big tiles never reshuffle when a live snapshot re-sorts the gallery); panoramas are dims-gated (`w/h ≥ 1.7`) and **outrank** crests. `GALLERY_COLS = 3` in `app.js` and `repeat(3, 1fr)` in `index.html` are coupled — a read-the-file invariant test pins them in lockstep.
- Tests are dependency-free (`node:test` + `node:assert/strict`). Pure logic (e.g. `haversineMeters`, `safeUrl`) is unit-tested directly. Render functions (`renderDay`) are tested with a small hand-rolled DOM stub in `app.test.js` (no jsdom) — reuse that stub for downstream screens; real-browser behavior (crossfade, layout) is covered by the VERIFY-APP stage, not unit tests. **Stub SVG gotcha:** the stub has a `createElementNS(_ns, tag)` shim, but `StubElement.setAttribute('class', …)` stores into `attributes` only — it does NOT populate `classList`. So an SVG element's class (HTML code sets it via `setAttribute`, since SVG `.className` is a read-only `SVGAnimatedString`) is invisible to `byClass`/`firstByClass`/`classList.contains` — assert it via `getAttribute('class')`. HTML elements built by `el()` (which sets `.className`) work fine with `byClass`.
- **Browser-verifying the app without the auth password:** `index.html` is behind the Firebase password gate, but `app.js`'s `boot()` **fails open when there is no `#login-overlay` in the DOM** (`if (!overlay||!form||!passwordInput){ mountTheApp(); return; }`) — *before* any Firebase import. So to drive the real UI in a headless browser with no password/network, serve a scratch copy of `index.html` with only the `<div id="login-overlay">…</div>` block deleted (keeps the theme CSS + `#app-root` + the `app.js` module script). Combine with the `?now=<mid-trip ISO>` time-travel override (today is pre-trip → the day-nav only renders during/after the trip). To exercise an injected handler (e.g. `onAddPhotos`), `import('./app.js')` in the page and call `mountApp(div, { onAddPhotos })` directly.
- **≥44px tap targets with a smaller visible circle:** the day-nav's circular buttons (`.day-nav-hamburger`/`.day-nav-prev`/`.day-nav-next`) keep a ≥44px hit area on the `<button>` itself (the base `.day-nav-btn` `min-width/min-height: 44px`) while the visible ~30px circle is drawn by a `::before` (centered, `z-index:-1` scoped by `isolation:isolate` so it sits behind the glyph but above the nav background). Don't collapse the button down to the circle's size — that was the original AC-miss. The ☰ glyph is an **inline SVG** (`buildHamburgerIcon`, SVG-namespaced via `createElementNS`/`svgEl`), not a Unicode character — the test stub needs a `createElementNS` shim (it has one). The popover rows are built via `buildMenuItem(text, iconSvg)` (leading SVG icon + `.nav-menu-label` span; `textContent` still reads as the label since the SVG has no text), separated by a non-focusable `role="separator"` `.nav-menu-divider`.
